## 0. 現在地（2026-09-21 時点）

- 稼働: Raspberry Pi 4（backend: FastAPI + discord.py、単一プロセス）+ Vercel（frontend: Next.js）+ Cloudflare Tunnel
- できること: YouTube/YouTube Music の検索・再生・キュー・関連曲・おすすめ（YouTubeアカウント個人化）、Web からの操作、VC 自動入室、再生履歴（SQLite・サーバー別・誰が入れたか）、リアルタイム同期（WebSocket）
- 直近の地盤固め（本文書と同セッション）:
  - **デプロイ跨ぎのレジューム**（無停止アップデート①）: 再起動しても同じ曲の同じ位置から自動再開。キューも維持
  - **Discord ログイン永続化**: アクセストークンの自動リフレッシュ + 90日セッション
  - 自動入室のゾンビ修復、yt-dlp 403 復旧、同時追加の堅牢化 など

**現状の一言評価**: 「音楽再生」は実運用で十分な完成度。プラットフォーム化の"土台"（認証・状態永続化・リアルタイム同期・履歴DB）は既にかなり揃っている。ここから機能を横に広げられる段階。

## 1. ビジョン: 「ドデカサーバーのリビング」

Discord は「話す・集まる」場所だが、**「今みんなで何をしているか」を束ねて可視化し、次の行動へのハードルを下げる**レイヤーは薄い。
イリーナが狙うのはそこ ——「音楽が鳴っている部屋」を起点に、**通話募集・ゲーム募集・ワイワイの記録**が自然に集まる場所。

3つの設計原則:
1. **摩擦を消す**: 「@here カスタムやる人」「何時から？」のような毎回の調整コストを、ボタン1つ・自動集計に。
2. **その場のノリを増幅する**: 盛り上がりを可視化（今VCに何人・何を聴いた・誰がよく盛り上げてる）して、内輪の一体感を強める。
3. **押し付けない**: 通知やAIは「optional な副操縦士」。既存の Discord の使い方を壊さない。

---

## 2. まず必要な"守り"の改善（プラットフォーム化の前提）

拡張する前に、土台の穴を塞ぐ。ここが弱いと機能を足すほど脆くなる。

| # | 項目 | 現状 | 対応 | コスト |
|---|---|---|---|---|
| S1 | **プロセス分割（無停止②）** | Web API と音声 bot が同一プロセス。検索/おすすめの修正でも音が止まる | 「音声プロセス」と「API/ワーカープロセス」を分離。API 側の更新は音声に無影響に。音声側更新もレジューム①で数秒で復帰 | 中 |
| S2 | **cookies.txt の失効運用** | YouTube cookie は手動。失効で再生/おすすめが劣化 | 失効検知 → 通知（Discord DM か Web バナー）。更新手順を1コマンド化 | 小 |
| S3 | **ディスク肥大** | music キャッシュ 1.7GB / 残 7.4GB、掃除機構なし | LRU で上限（例5GB）を超えたら古い順に削除。アップロード曲は対象外 | 小 |
| S4 | **秘密情報の集中** | Discord/YouTube/各種トークンが .env に平置き | 段階的に整理（最低限バックアップ）。将来の OAuth 拡張(§4)前に一度棚卸し | 小 |
| S5 | **観測性** | 障害は事後にログを掘る | `/` ヘルスに主要指標（接続数・エラー率・cookie 残日数）を出し、Web に小さな状態パネル | 小〜中 |

**S1 を最優先**にする理由: プラットフォーム化＝機能追加の回数が増える＝デプロイ頻度が上がる。音声を巻き込まずに出せる体制がないと、「更新するたびに音楽が止まる」体験が拡張の足かせになる。

## 3. 拡張アイデア（プロダクト）

> ⚠️ 各アイデアの"刺さり度"は、ドデカサーバーの実際の会話傾向で検証すべき（§5参照。現状は未取得）。
> 以下は既知の事実（gaming community・VC 中心・音楽が既存の入口・自動入室が ゲーム チャンネルで発火）からの推定。

### A. 音楽体験の深掘り（既存の強みの延長・すぐ効く）
- **A1. みんなの再生ランキング / 週間まとめ**（コスト小）: 既にある `play_history` を使い、「今週このサーバーで流れた曲 TOP」「よく入れる人」を Web と Discord 埋め込みで。→ 内輪の会話ネタになる
- **A2. 「ドデカの1曲」= サーバー共同プレイリスト**（コスト中）: 高評価/保存でサーバー独自のプレイリストが育つ。SQLite に guild 別プレイリストテーブル
- **A3. 途中参加者への"今の曲"表示強化 / リクエスト予約**（コスト小）

### B. 集まる摩擦を消す（プラットフォームの核・要検証だが本命）
- **B1. ワンタップ通話募集**（コスト中）: Web/スラッシュコマンドで「21時から Apex カスタム、4人募集」→ Discord に参加ボタン付きで投稿、集まったら通知。「@here 誰かやる？」の定型を置き換え
- **B2. 日程調整の軽量版**（コスト中）: 「今夜やる人？」に絵文字/ボタンで、Web に集計。ちょうど良い時間を提案
- **B3. VC の"今"ダッシュボード**（コスト小〜中）: 誰がどの VC に何人、何を聴いているか。ドデカのトップページに

### C. ゲームコミュニティ機能（要検証・中〜大）
- **C1. カスタム/スクリム募集テンプレ**（ゲーム別）: よく遊ぶタイトルの募集フォーマットをボタン化
- **C2. 簡易チーム分け / ランダムマッチ**（コスト小）: VC 参加者からワンタップでチーム分け
- **C3. 戦績/スコアの記録**（コスト大・需要次第）: 手入力 or 外部API。需要が確認できてから

### D. AI 副操縦士（optional・イリーナのキャラを活かす）
- **D1. 気分/シーンからのプレイリスト生成**（コスト中）: 「作業用」「盛り上がる」で選曲。既存 mood API + LLM
- **D2. サーバーの空気の要約**（コスト中・プライバシー配慮必須）: 「今日の盛り上がり」を軽く要約。**オプトイン前提**
- **D3. イリーナのキャラ対話**（既にチャット下地あり）: 節度を持って

## 4. OAuth / 認証の将来設計（拡張の土台）

現状は NextAuth + Discord OAuth（scope: `identify guilds`）でログインするだけ。プラットフォーム化に向けては:

- **N1. scope の段階拡張**: 機能が要求する最小限だけ足す。例:
  - `guilds.members.read`（サーバー内メンバー情報 → B系の募集/チーム分け）
  - `messages.read` 系は**入れない方針**（プライバシー影響大。会話分析は bot 側の限定運用で）
- **N2. "Sign in with Discord" を軸にしたユーザーモデル**: Discord user id を主キーに、per-user 設定（好み・通知オプトイン）を SQLite（or 将来の DB）に。§ 既存の added_by_id と統合
- **N3. 通知チャンネルの同意管理**: DM/バナーで通知するなら、ユーザーごとのオプトイン状態を持つ
- **N4. トークン運用の堅牢化**（今回入れた refresh の延長）: refresh 失敗の可視化、scope 追加時の再同意フロー
- **将来**: YouTube 個人化を「オーナーの cookie 共用」から脱却したいなら YouTube OAuth も選択肢だが、サーバー全員の体験が1アカウントに紐づく現状の割り切りで十分なら急がない

## 5. ドデカサーバー会話分析（未実施・要オーナー承認）

- 目的: §3 のアイデアの優先順位を"実際の会話"で裏付ける（どのゲーム・どんな募集・音楽への不満）
- 方法: bot トークンで直近の各テキストチャンネルを読み、集計（サブエージェント / 軽量モデル）
- 状態: **今回、安全分類器によりサブエージェント起動がブロックされた**。オーナーの明示的な承認（または権限ルールの追加）があれば実行する。生の会話全文は保存せず、集計と少数の引用のみをレポート化する運用にする

## 6. 推奨ロードマップ（順序）

1. **完了済み（土台）**: レジューム① / ログイン永続化 / 自動入室修復
2. **次（守り）**: S1 プロセス分割（無停止②）← 最優先。S3 キャッシュ掃除、S2 cookie 失効通知
3. **すぐ効く攻め**: A1 週間まとめ / B3 VC ダッシュボード（既存データで作れて、内輪で刺さりやすい）
4. **会話分析（§5）で検証**してから B1/B2（募集・調整）→ C 系
5. **AI（D系）は後半**。土台と実需要が固まってから

各ステップは「1機能ずつ・テスト付き・音声を止めずにデプロイ」（レジューム①とプロセス分割②の上で）を守る。

## 付録: 「無停止アップデート」の現実解（技術メモ）

- Discord は **1 bot トークン = 1ギルド1ボイス接続**。同トークンで新旧2プロセスを同時起動すると close 4006/4017 で衝突 → Web 流のブルーグリーンは音声に不可
- したがってゴールは「音が1秒も切れない」ではなく **「数秒無音 → 同じ曲の続きから自動再開」**（レジューム①で達成済み）
- さらに **プロセス分割②** で、API/フロント寄りの変更は音声プロセスに一切触れずデプロイ可能になる（音声を止めるのは音声コアを触った時だけ）
- テスト用 bot トークン（`TEST_DISCORD_TOKEN`）を用意済み。②の検証やローカル開発で本番 bot と衝突せずに使える
